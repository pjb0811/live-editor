# Drag & Drop

`Live.Dnd` lets you build UIs visually. At wider sizes, drag a component from
the left palette onto the canvas, then edit its properties from the panel on
the right; below `Live.Dnd`'s own responsive breakpoint, the palette and
panel move into a drawer instead, and a tap adds the section (there's nothing
visible to drag onto once the canvas is stacked behind the drawer). Powered
by [`@dnd-kit`](https://dndkit.com/).

```tsx
import { useState } from 'react';

import Live from '@jbpark/live-editor';
import { createDocument } from '@jbpark/live-editor/utils';

export default function DragAndDrop() {
  const [value, setValue] = useState(() => createDocument());

  return (
    <Live>
      <Live.Dnd
        value={value}
        onChange={setValue}
        dynamicTailwind
        frame={{ mode: 'shadow', syncStyle: true }}
      />
    </Live>
  );
}
```

- `value` / `onChange` hold the generated source — drops and property edits are
  applied through the same AST pipeline, so the code stays canonical. Start
  from `createDocument()`, not an empty string: see
  [Document structure](#document-structure).
- `frame` configures the preview surface (see [Preview Modes](./preview-modes.mdx)).
- Use `items` to customize the palette's available sections. Mark what the
  panel can edit in each section with `data-binding` — see
  [Data Binding](./data-binding.mdx).
- A section's name, shown on the canvas and in the panel, comes from its
  `data-name`. A `<section>` without one is named by `sectionNameFallback`,
  which gets the section's 0-based position. The default gives `Section 1`,
  `Section 2`, and so on.
- Use `children` to replace the built-in UI — a region of it
  (`<Live.Dnd.Layout panel={...} />`) or the whole arrangement, driven from
  the `useDndPalette()` / `useDndPanel()` / `useDndLayout()` hooks — see
  [Custom Palette & Panel](./custom-palette-panel.mdx).

The embedded demo above runs the real `Live.Dnd` component, isolated with
`shadow` mode inside a sandboxed iframe (see
[Preview Modes](./preview-modes.mdx)).

## Section toolbar

A selected section shows four buttons in its top-right corner: move up, move
down, duplicate and delete. Move up is disabled on the first section and move
down on the last. The move buttons make the same move as the panel's, so a
section can be reordered without a drag even when a custom panel leaves move
controls out.

In the built-in mobile layout, selecting a section opens the panel in a
drawer, which has the same buttons.

## Keyboard

Palette cards and canvas sections can be reached with Tab.

| Key | On a palette card | On a canvas section |
| --- | --- | --- |
| Enter | Adds the section to the canvas | Selects the section (or clears the selection), like a click |
| Arrow Up / Arrow Down | — | Goes to the previous or next section and selects it |
| Home / End | — | Goes to the first or last section and selects it |
| Delete or Backspace | — | Deletes the section (through `onBeforeDelete`) and moves focus to the next one |
| Space | Picks the card up to drag it | Picks the section up to move it |
| Arrow keys, while picked up | Move what's picked up | Move the section |
| Space or Enter, while picked up | Drops it | Drops it at the new position |
| Escape, while picked up | Cancels the drag | Cancels the move |

Screen readers hear the section's name and its new position while it moves.
The selected section is scrolled into view whenever it moves out of sight, from
the keyboard or from the move buttons on the canvas or in the panel.

## Confirming a delete

Deleting a section is immediate. Pass `onBeforeDelete` to ask first: it gets
the section, and returning `false`, or a promise of `false`, keeps it. It runs
for the delete button on the canvas, the one in the panel, and a custom
panel's `onDelete`. The library shows no dialog of its own.

```tsx
<Live.Dnd
  value={value}
  onChange={setValue}
  onBeforeDelete={section => confirm(`Delete ${section.name}?`)}
/>
```

A promise is waited for, and the section is removed from the document as it
is when the answer comes, so edits made while your dialog was open are kept.
If `onBeforeDelete` throws or rejects, the section is kept.

## Picking an element

The crosshair button at the bottom-left of the canvas turns on the element
picker. While it's on, the element under the pointer is outlined, and a click
selects that element's section and brings its fields into view in the panel,
including fields nested in an Items or Children editor. The picker turns off
after a pick, and Escape turns it off without one. Sections can't be dragged
while it's on.

`onNodePick` reports each pick: the element's `data-id`, which is the `id` its
fields carry in `useDndPanel().bindings`, and its section's id.

```tsx
<Live.Dnd
  value={value}
  onChange={setValue}
  onNodePick={({ id, sectionId }) => console.log(id, sectionId)}
/>
```

A custom layout or panel drives the picker with `useDndInspector()`:

| Field | Type | Description |
| --- | --- | --- |
| `active` | `boolean` | Whether the picker is on. |
| `activate` / `deactivate` / `toggle` | `() => void` | Turns it on or off. |
| `picked` | `{ id: string; sectionId: string } \| null` | The last element picked, until another section is selected. A custom panel can use it to show that element's fields. |

```tsx
import { useDndInspector, useDndPanel } from '@jbpark/live-editor/dnd';

const MyPanel = () => {
  const { picked, toggle, active } = useDndInspector();
  const { bindings } = useDndPanel();
  const fields = picked
    ? bindings.filter(binding => binding.id === picked.id)
    : bindings;

  return (
    <>
      <button aria-pressed={active} onClick={toggle}>
        Pick an element
      </button>
      {/* render `fields` */}
    </>
  );
};
```

What can be picked:

- An element is picked by its `data-id`, so the picker finds the nearest
  element at or above the pointer that has one. Empty ids are filled for the
  preview the same way the panel fills them (see
  [Data Binding](./data-binding.mdx)).
- A component that doesn't pass `data-*` attributes through to its DOM can't
  be picked itself. Clicking it picks the nearest element above it that has a
  `data-id`.
- It works the same in every frame mode: in an iframe, in a shadow root, or
  rendered in place.
- Fields inside a collapsed array item aren't shown, so the panel can't bring
  them into view until the item is expanded.

## Document structure

`Live.Dnd` edits one component's source. Its sections are the `<section>`
elements inside a container element, found by its `id`:

```tsx
const App = () => {
  return (
    <main id="app-container">
      <section data-name="Hero" data-id="a1b2c3">
        {/* ... */}
      </section>
      <section data-name="Features" data-id="d4e5f6">
        {/* ... */}
      </section>
    </main>
  );
};

export default App;
```

- The container is the element whose `id` is `app-container`. The tag doesn't
  matter. To use another id, pass it as `containerId`, both to `Live.Dnd` and
  to `createDocument({ containerId })`.
- Each `<section>` inside the container is one section on the canvas, in
  source order, even when it's wrapped in other elements. A `<section>` nested
  inside another belongs to its parent.
- `data-name` is the section's name; see `sectionNameFallback` above for
  sections without one. `data-id` identifies the section across edits.
  `Live.Dnd` gives every section that lacks one an id the next time it commits
  an edit, so you don't need to write it by hand.
- `createDocument()` from `@jbpark/live-editor/utils` returns an empty
  document in this shape. Without a `value`, `Live.Dnd` starts from the same
  document.

A document without the container has no sections, and nothing added from the
palette can land in it. `Live.Dnd` reports this once through `onEditError`, or
a toast by default, with `type: 'parse'`, `target: 'document'` and
`reason: 'container-not-found'`. The canvas names the missing id too.

A document that doesn't parse is usually one being typed in the code editor.
The canvas and panel keep showing the last version that parsed, with a notice
that it's out of date, and stay read-only until the source parses again. An
edit tried in the meantime isn't applied: it's reported through
`onEditError` with `reason: 'parse-error'`. If the document has never parsed,
the canvas says it has a syntax error.

## Sections that fail

A section that fails to compile, or throws while rendering, shows an error box
in its slot on the canvas; the other sections keep working. To show your own
placeholder instead, pass `renderSectionFallback`:

```tsx
const retired = new Set(['Legacy Banner']);

<Live.Dnd
  value={value}
  onChange={setValue}
  renderSectionFallback={({ section, reason, message }) => (
    <div className="rounded border border-dashed p-6 text-center">
      {section.name} is unavailable
      {reason !== 'forced' && <small>{message}</small>}
    </div>
  )}
  shouldForceSectionFallback={section => retired.has(section.name)}
/>
```

| `reason` | When | `message` |
| --- | --- | --- |
| `'compile'` | The section's code doesn't compile. | The compiler's message. |
| `'runtime'` | The section threw while rendering. | The error's message. |
| `'forced'` | `shouldForceSectionFallback` returned `true`. | `undefined` |

- Return `undefined` to keep the built-in error box for that case.
- `shouldForceSectionFallback` runs before a section is compiled. A section it
  selects is never compiled, so none of its top-level code runs. Use it for
  sections you know can't work, such as ones that import a component your
  `modules` no longer provide.
- A runtime fallback renders inside the section's frame, where the section's
  own content would have been. In `iframe` mode it only gets the host's styles
  with `frame.syncStyle`, so prefer inline styles there. Compile and forced
  fallbacks render outside the frame.
- Fixing a section's code recovers it automatically.
- If your fallback itself throws, that section falls back to the built-in
  error box. The canvas keeps working.

## Keeping edits fast

Each canvas section re-renders only when its own inputs change, so an edit to
one section doesn't redraw the rest. Two props are compared by reference,
because the library can't tell whether a new function or object does the same
thing as the old one:

- **`provider`**: an inline arrow function is a new function on every render.
- **Objects and functions inside `props`**: `props={{ theme: { dark: true } }}`
  creates a new `theme` object on every render. Strings, numbers and booleans
  are fine.

Written inline, either one re-renders every section on every edit. In a large
document that's slow: at 90 sections it made each edit take over a second.
Define them outside the component, or keep them stable with `useCallback` or
`useMemo`:

```tsx
// Outside the component: the same function on every render.
const withTheme = (children: React.ReactNode) => (
  <ThemeProvider>{children}</ThemeProvider>
);

export default function Page() {
  const [value, setValue] = useState(() => createDocument());

  return (
    <Live>
      <Live.Dnd value={value} onChange={setValue} provider={withTheme} />
    </Live>
  );
}
```

A provider that depends on state still works; pass it through `useCallback`
with that state as a dependency, and sections re-render when the state
changes.

`frame` and `modules` don't need this. They are compared by value, so writing
them inline is fine.
