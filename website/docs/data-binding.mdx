# Data Binding

A palette section becomes editable in the property panel through two
attributes on its elements:

- `data-id`: the element's identity. Leave it empty (`data-id=""`) in palette
  sections. `Live.Dnd` fills an empty one from the section's own id, in
  document order (`<section id>-1`, `-2`, ...), and the panel and the canvas
  preview use the same ids. They're written into the source with the first
  edit to that section, so opening a document doesn't change it.
- `data-binding`: an array describing which props of that element the panel
  can edit, and how.

```tsx
<h1
  data-id=""
  data-binding={[{ label: 'Title', property: 'innerText', required: true }]}
>
  Welcome
</h1>
```

Each entry in the array is one field in the panel. The rest of this page lists
what an entry can declare.

The default palette (the sections `Live.Dnd` shows when you pass no `items`)
uses every option on this page. Its **Roadmap** section is the most complete
example, and you can try it in the [Drag & Drop](./drag-and-drop.mdx) demo.

## Who owns what

The library owns what a value **is** and what it **may be**: its data kind
(`type`) and its constraints (`min`, `max`, `pattern`, `required`). The
built-in panel picks a default control from those and validates edits against
them.

How a field is **drawn** belongs to the panel. `widget` is carried through to
your panel untouched; the built-in panel never reads it. The library ships no
widgets, so a `widget` value does nothing until your own code handles it (see
[`widget`](#widget-a-hint-for-your-own-controls)). Switch on it in
[`renderField`](./custom-palette-panel.mdx#replacing-one-control-everywhere-renderfield)
to replace individual controls while keeping the built-in panel, or in a
[custom panel](./custom-palette-panel.mdx#choosing-a-control-is-the-panels-job).

## Fields

| Field           | Type                                        | Meaning                                                                                                                                                                          |
| --------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `label`         | `string`                                    | **Required.** The field's heading in the panel. Must be unique within one element.                                                                                               |
| `property`      | `string`                                    | The prop to edit. See [Properties](#properties). Can be omitted only for `type: 'richtext'`, which then edits `innerHTML`.                                                       |
| `type`          | `BindingType`                               | The data kind. Picks the default control and how the value is validated and written back. See [Types](#types).                                                                   |
| `options`       | `{ label: string; value: string }[]`        | A fixed set of values. The built-in panel shows a select.                                                                                                                        |
| `min` / `max`   | `number`                                    | Range for a number value.                                                                                                                                                        |
| `pattern`       | `string`                                    | A regular expression (as a string) a text value must match.                                                                                                                      |
| `required`      | `boolean`                                   | An empty value is rejected.                                                                                                                                                      |
| `render`        | `BindingRenderMap`                          | Types the keys inside an `object` or `array` value. See [Nested fields](#nested-fields).                                                                                         |
| `widget`        | `string` or `{ type: string; ...settings }` | A control name **you** define, plus any settings your control needs. Not a built-in option; ignored by the built-in panel. See [`widget`](#widget-a-hint-for-your-own-controls). |
| _any other key_ | `unknown`                                   | Kept as-is under `binding.meta` for your own panel (a group name, a hint, ...).                                                                                                  |

A malformed value never removes the field. An unknown `type`, a `min` that is
not a number, or an invalid `widget` is dropped on its own, and the rest of the
entry still works.

## Properties

`property` names what the field edits:

| `property`       | Edits                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------ |
| `innerText`      | The element's text content.                                                                            |
| `innerHTML`      | The element's HTML content. Used by `type: 'richtext'`.                                                |
| `children`       | The element's JSX children, as a reorderable list.                                                     |
| `items` / `data` | An array prop, as a list of items you can add, move, duplicate and delete.                             |
| any other name   | That JSX attribute, e.g. `size`, `href`, `style`. It doesn't have to be on the element yet: see below. |

`innerText` and plain `innerHTML` go between the element's tags, so they need
an element with a closing tag. Writing either to a self-closing element such
as `<img />` is refused with the reason `self-closing`; clearing it does
nothing and succeeds. `type: 'richtext'` writes `dangerouslySetInnerHTML`, so
it works on a self-closing element too.

### Optional attributes

A binding can name an attribute the element doesn't carry. Committing a value
adds it, after the element's last attribute. Committing `undefined` removes an
attribute, and to React a prop that's `undefined` and one that's missing are
the same. So one binding can switch an optional prop off and on:

```tsx
onChange(undefined); // <a title="Docs" target="_blank"> → <a title="Docs">
onChange('_blank'); //  <a title="Docs"> → <a title="Docs" target="_blank">
```

- An empty string writes `prop=""` on an attribute that's there, and leaves a
  missing one missing.
- For `innerText` and `innerHTML`, `undefined` empties the content.
  `children` can't be removed as a whole.
- A binding with `required: true` can't be removed. The edit is refused.
- `PanelBinding.present` is `false` while the attribute is missing, which is
  what a custom panel reads to draw an on/off switch. `prop=""` counts as
  present.

Because a missing attribute is added instead of reported, a typo in
`property` shows up as an unexpected attribute in the source rather than as an
error.

`data-id`, `data-name`, `data-binding` and `data-binding-key` are managed by
the editor, so a
binding can't target them. A field on one of these is shown as read-only, and
an edit to it is refused with an error naming the property.

## Binding the section itself

The `<section>` element takes a `data-binding` like any other element, which is
how a panel edits the section's own background, padding or spacing. Its fields
come first in the panel, ahead of the elements inside it.

```tsx
<section
  data-name="Banner"
  data-binding={[
    {
      label: 'Section Style',
      property: 'style',
      type: 'object',
      render: {
        backgroundColor: { type: 'color', label: 'Background' },
        paddingBlock: {
          type: 'number',
          label: 'Vertical Padding',
          min: 0,
          max: 160,
          widget: 'slider',
        },
      },
    },
  ]}
  style={{ backgroundColor: '#4f46e5', paddingBlock: 64 }}
>
  {/* ... */}
</section>
```

Try it in the [Drag & Drop](./drag-and-drop.mdx) demo: the **Banner (bound
section)** at the end of the palette is this section. Add it, select it, and
change its background or padding from the panel.

The library ships no bindings on the default sections: which properties of a
section are editable, and what they're called, is up to you. Because the
binding is part of the section's source, it's copied and moved along with the
section, and each copy stays editable.

## Binding every element of a component

Repeating the same `data-binding` on every button or title gets long, and the
array stays in the code the editor produces. Pass `bindings` to `Live.Dnd`
instead: a map from a component's tag name to the entries every element of
that component gets. The markup then only needs a `data-id`.

```tsx
import type { BindingRegistry } from '@jbpark/live-editor/utils/ast';

// Defined once, outside the component.
const bindings = {
  'ui.Button': [
    { label: 'Button Text', property: 'innerText' },
    {
      label: 'Size',
      property: 'size',
      options: [
        { label: 'Small', value: 'small' },
        { label: 'Large', value: 'large' },
      ],
    },
  ],
  'ui.Typography.Title': [
    { label: 'Heading', property: 'innerText', required: true },
  ],
} satisfies BindingRegistry;

<Live.Dnd value={code} onChange={setCode} bindings={bindings} />;
```

```tsx
<section data-name="Intro">
  <ui.Typography.Title data-id="" level={2}>
    Welcome
  </ui.Typography.Title>
  <ui.Button data-id="" size="small">
    Get Started
  </ui.Button>
</section>
```

- **Components only.** A key is a component's name: a member path
  (`ui.Button`) or a name that doesn't start with a lowercase letter
  (`Button`). HTML elements such as `p` or `h2` can't be keys, since an entry
  for one would make every paragraph or heading in every section editable.
  `satisfies BindingRegistry` rejects those keys, and `Live.Dnd` ignores them
  at runtime with a console warning. Bind an HTML element with its own
  `data-binding`, or [by key](#binding-by-key).
- **Names are matched as written.** `<ui.Button>` matches `'ui.Button'`. The
  same component imported as `import { Button } from ...` is `<Button>` and
  needs a `'Button'` entry.
- **An element's own `data-binding` wins**, whole: its entries replace the
  registry's for that element instead of being merged with them. Use it for the
  one element that should be edited differently. `data-binding={[]}` makes an
  element not editable at all.
- **Every element still needs a `data-id`**, as with an inline binding.
- Entries take everything an inline entry does, and are validated the same
  way. That includes keys of your own, such as `group` or `tab`, which arrive
  in `binding.meta` (see [Common `meta` keys](#common-meta-keys)). The type of
  one entry is `BindingSchema`.
- It applies everywhere bindings are read: the built-in panel, `useDndPanel()`,
  `Live.Dnd.Field`, and the elements found inside `items` and `children`
  values. The AST helpers take it as an option too:
  `extract(source, { bindings })` and `update(..., { bindings })` /
  `updateAll(..., { bindings })`.
- Define it once, outside render. A new object on every render makes
  `Live.Dnd` read every section again.

## Binding by key

The component registry gives every element of a component the same fields. For
an HTML element, or for one element whose fields or labels differ from the
rest, name the schema in the markup with `data-binding-key` and define it in
`bindingKeys`:

```tsx
import type { BindingKeyMap } from '@jbpark/live-editor/utils/ast';

// Defined once, outside the component. Plain data, so it can come from JSON
// or a CMS.
const bindingKeys = {
  'hero-title': [
    { label: 'Hero Title', property: 'innerText', required: true },
  ],
  'hero-cta': [
    { label: 'CTA Text', property: 'innerText' },
    { label: 'CTA Link', property: 'href', type: 'url' },
  ],
} satisfies BindingKeyMap;

<Live.Dnd
  value={code}
  onChange={setCode}
  bindings={bindings}
  bindingKeys={bindingKeys}
/>;
```

```tsx
<section data-name="Hero">
  <h1 data-id="" data-binding-key="hero-title">
    Welcome
  </h1>
  <a data-id="" data-binding-key="hero-cta" href="/start">
    Get started
  </a>
</section>
```

- **Any element.** HTML elements and components alike, since an element only
  gets fields when its markup names a key.
- **Precedence.** An element's own `data-binding` comes first, then the key its
  `data-binding-key` names, then its component's registry entry. Each replaces
  the next whole. An element with both `data-binding` and `data-binding-key`
  uses its `data-binding`, and the console warns about it.
- **A key that isn't in `bindingKeys`** gives the element no fields, without
  falling back to the registry, and the console names the key once. So does a
  `data-binding-key` that isn't a plain string.
- **Every element still needs a `data-id`**, and `data-binding-key` can't be
  the target of a binding.
- Entries are `BindingSchema`s, as in the registry, so keys of your own
  arrive in `binding.meta` here too.
- The AST helpers take both maps in one options object:
  `extract(source, { bindings, bindingKeys })`, and the same for `update()` and
  `updateAll()`. A custom panel gets that object from
  `useDndPanel().bindingOptions`.

### Where the schema lives

An inline `data-binding` travels with the section's source, so a saved
document stays editable wherever it's opened. With `bindings` or
`bindingKeys`, the schema lives in your code instead, and a saved document is
only editable where the same maps are passed. Keep the maps with the documents
that use them, and keep a key's name once documents refer to it.

## Types

| `type`     | Built-in control                           | Validation                       |
| ---------- | ------------------------------------------ | -------------------------------- |
| `string`   | Text area                                  | `required`, `pattern`            |
| `number`   | Number input                               | `required`, `min`, `max`         |
| `boolean`  | Checkbox                                   | —                                |
| `color`    | Color picker                               | —                                |
| `date`     | Date picker (value stored as `YYYY-MM-DD`) | `required`, valid date           |
| `url`      | URL input                                  | `required`, `pattern`, valid URL |
| `richtext` | Rich text editor                           | —                                |
| `jsx`      | Code editor                                | —                                |
| `object`   | One nested field per key                   | per nested field                 |
| `array`    | Item list                                  | per nested field                 |

Without a `type`, the built-in panel picks a control from the current value (a
checkbox for `true`, a number input for `42`, and so on). A property whose name
contains `color` also gets a color picker. `options` replaces the text, number,
color, date and URL controls with a select.

## Constraints

`min`, `max`, `pattern` and `required` are checked before an edit is committed.
A rejected edit shows its message under the field and leaves the source
unchanged:

```tsx
{
  label: 'Content Spacing',
  property: 'size',
  type: 'number',
  min: 0,
  max: 40,
}
```

Typing `99` shows _Must be at most 40._ Custom panels can run the same check
with `validateBindingValue(binding, value)`. To show these messages in
another language, see [Localization](./localization.mdx#validation).

## Nested fields

For an `object` or `array` value, `render` describes the keys inside it. An
entry that declares `type` is a **leaf**, and a leaf accepts every field a
top-level entry does: `label`, `options`, constraints, `widget`, a nested
`render`, and extra keys for `meta`. `label` and `property` fall back to the
key.

An `object` binding, from the default Hero section:

```tsx
<ui.Space
  data-id=""
  data-binding={[
    {
      label: 'Background Style',
      property: 'style',
      type: 'object',
      render: {
        backgroundColor: { type: 'color', label: 'Background Color' },
      },
    },
  ]}
  style={{ backgroundColor: '#6366f1' }}
/>
```

An `array` binding, trimmed from the default Roadmap section. Each item gets one
field per key, labeled and validated by its leaf. `link` is itself an `object`
leaf with its own `render` map:

```tsx
<ui.List
  data-id=""
  data-binding={[
    {
      label: 'Milestones',
      property: 'data',
      type: 'array',
      render: {
        title: { type: 'string', label: 'Title', required: true },
        date: { type: 'date', label: 'Release Date', required: true },
        status: {
          type: 'string',
          label: 'Status',
          options: [
            { label: 'Planned', value: 'planned' },
            { label: 'Shipped', value: 'shipped' },
          ],
        },
        progress: { type: 'number', label: 'Progress', min: 0, max: 100 },
        color: { type: 'color', label: 'Accent Color' },
        highlight: { type: 'boolean', label: 'Highlight' },
        link: {
          type: 'object',
          label: 'Link',
          render: {
            text: { type: 'string', label: 'Link Text' },
            href: { type: 'url', label: 'Link URL', pattern: '^https://' },
          },
        },
      },
    },
  ]}
  data={[
    {
      title: 'Visual editing',
      date: '2026-03-02',
      status: 'shipped',
      progress: 100,
      color: '#22c55e',
      highlight: false,
      link: { text: 'Release notes', href: 'https://github.com' },
    },
  ]}
  renderItem={item => <div>{/* ... */}</div>}
/>
```

A `render` entry without `type` is treated as a plain group of further entries.
It cannot have a label of its own, so prefer an `object` leaf as above.

JSX-valued keys inside an item (`children`, or a key holding an element) are
not typed through `render`. The panel shows the bindings declared on those
elements instead, or a code editor when they declare none.

## Presentation and metadata

Two ways to pass information to a custom panel without the library acting on
it:

```tsx
{
  label: 'Scroll Speed',
  property: 'speed',
  type: 'number',
  min: 20,
  max: 300,
  widget: { type: 'slider', step: 10 },
  group: 'motion',
}
```

- `widget` names the control your panel should draw. See below.
- Any key the library does not define (`group` above) arrives under
  `binding.meta.group`.

Both reach your code the same way, so you could put the control name in
`meta` too (`control: 'slider'` arrives as `binding.meta.control`). Use
`widget` for it anyway. It's a reserved field, so it keeps its place if the
library adds new fields later, while a `meta` key that becomes a library
field moves out of `meta`. It's also the one name `renderField`, custom
panels and nested fields all check for the control. Use `meta` for the other
information about a field, such as a group or help text.

The built-in panel shows a number input for this field and ignores both.

### `widget`: a hint for your own controls

`widget` is not a list of built-in controls to choose from. The library ships
no widgets, and `'slider'` is not a built-in option either; it's just the name
these docs and the demos use. Nothing happens to a `widget` value until your
own code reads it:

1. You pick a name for the control you want and write it on the binding.
2. Your code checks `binding.widget.type` in
   [`renderField`](./custom-palette-panel.mdx#replacing-one-control-everywhere-renderfield)
   or in a [custom panel](./custom-palette-panel.mdx#choosing-a-control-is-the-panels-job)
   and draws that control.
3. Anywhere the name isn't handled, including the built-in panel, the field
   gets the default control for its `type`.

Any string works, so name controls after what your panel actually draws. For
example:

| `widget`        | On a field with   | Your panel might draw                           |
| --------------- | ----------------- | ----------------------------------------------- |
| `'slider'`      | `type: 'number'`  | A range slider using `min`, `max` and `step`    |
| `'switch'`      | `type: 'boolean'` | A toggle switch instead of a checkbox           |
| `'radio'`       | `options`         | Radio buttons instead of a select               |
| `'textarea'`    | `type: 'string'`  | A multi-line text box with a given height       |
| `'icon-picker'` | `type: 'string'`  | Your own icon set, writing the chosen icon name |

None of these are built in; they only show the kind of names that fit.

`widget` is authored either as a bare string or as an object that also
carries the control's own settings:

```tsx
widget: 'slider'                                // arrives as { type: 'slider' }
widget: { type: 'slider', step: 4, unit: 'px' } // settings for your slider
widget: { type: 'textarea', rows: 6 }           // settings for your textarea
```

The bare string is normalized to `{ type }`, so your code always checks
`widget.type`.

The settings are yours too; the library reads none of them. `step` and
`unit` are the only two that come typed. That isn't because the library uses
them. They're common enough that your code gets them as `number` and
`string` instead of `unknown`. Every other setting (`rows` above) arrives as
`unknown`, so check its type before using it. A typed setting with the wrong
type (`step: '4'`) drops the whole `widget`, so your code sees
no widget on that field and draws its default control.

Keep value rules out of `widget`. `min`, `max`, `pattern` and `required`
belong on the binding itself, where the library enforces them whatever
control draws the field.

### Common `meta` keys

The library defines no presentation fields beyond `widget`, so help text,
grouping and visibility all go in `meta`. Nothing stops each app from
inventing its own names for them, so these docs suggest a shared set. The
library reads none of them, and the built-in panel ignores them all. They
only mean something once your panel reads them.

| Key           | Value               | Meaning                                                                         |
| ------------- | ------------------- | ------------------------------------------------------------------------------- |
| `description` | `string`            | Guidance the user always needs. Show it next to the field.                      |
| `hint`        | `string`            | Extra detail the user can choose to open, such as a tooltip or an info icon.    |
| `group`       | `string`            | Fields with the same name belong in one box.                                    |
| `tab`         | `string`            | Fields with the same name go on one tab.                                        |
| `visible`     | `boolean` or a rule | Whether to show the field. Leaving it out means visible. See [below](#visible). |

Keep `description` and `hint` apart. Text the user has to read is a
`description`. Putting it in a `hint` hides it behind a hover.

```tsx
data-binding={[
  {
    label: 'Link',
    property: 'mode',
    options: [
      { label: 'None', value: 'none' },
      { label: 'URL', value: 'url' },
    ],
    group: 'link',
  },
  {
    label: 'URL',
    property: 'href',
    type: 'url',
    description: 'Opens in the same tab.',
    group: 'link',
    visible: { property: 'mode', in: ['url'], default: 'none' },
  },
]}
```

#### `visible`

`visible: false` always hides the field. A rule shows it only while another
binding's value is one of a list:

```ts
type VisibleRule = {
  property: string; // the binding this field depends on
  id?: string; // that binding's element, when it isn't this field's own
  in: unknown[]; // show while the value is one of these
  default?: unknown; // the value to assume when the attribute is missing
};
```

- `property` refers to this field's own element by default. A section can
  carry the same property on several elements, so name another element with
  `id`, its `data-id`.
- When the value is an array, the field shows while any of its entries is
  in `in`.
- Set `default` whenever the property may be missing. Documents written before
  the property existed don't carry it. Without `default`, those documents
  would hide the field for good.
- Only bindings reach the panel, so the property a rule reads must have a
  binding of its own.

A hidden field is still in `bindings`, with its value and `onChange`, so your
panel can decide whether to leave it out or show it disabled. A panel might
check the rule like this:

```tsx
import type { PanelBinding } from '@jbpark/live-editor/dnd';

const isVisible = (binding: PanelBinding, bindings: PanelBinding[]) => {
  const rule = binding.meta?.visible as boolean | VisibleRule | undefined;

  if (rule === undefined || typeof rule === 'boolean') {
    return rule ?? true;
  }

  const source = bindings.find(
    item =>
      item.id === (rule.id ?? binding.id) && item.property === rule.property,
  );
  const value =
    source && source.present !== false ? source.value : rule.default;

  return Array.isArray(value)
    ? value.some(entry => rule.in.includes(entry))
    : rule.in.includes(value);
};

bindings.filter(binding => isVisible(binding, bindings));
```

`meta` values arrive as `unknown`, so check a rule's shape before relying on
it in production code.

#### A panel that reads them

The demo below is a custom panel built on `useDndPanel()` that reads all five
keys. The section's schema lives in `bindingKeys`, so the markup only carries
`data-binding-key`.

- **`tab`** puts the fields on a Content or a Style tab. A field without one
  goes on a General tab, and the tab bar only shows when there's more than one
  tab.
- **`group`** puts the button's fields in one Button box. On the Style tab,
  that box holds only the variant. A field without a `group` sits in a box for
  its element, the way the built-in panel groups fields.
- **`description`** shows under its field, and **`hint`** behind the icon next
  to the Text label.
- **`visible`** hides URL when Link is set to None.

Each field is still drawn by `Live.Dnd.Field`, so only the arrangement is the
demo's own. Its source is in
[`demos/panel-meta`](https://github.com/pjb0811/live-editor/tree/main/demos/panel-meta).
